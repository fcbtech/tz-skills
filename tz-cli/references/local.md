# `tz local` - the backend stack on this machine

Docker Compose project `tz-local`, compose file `~/.tz/local/docker-compose.yml` (regenerated by every `up`;
don't hand-edit). Same images, entrypoint and staging config as a Fargate stack.

## Commands
- `tz local up [-s v2|reporting|subhub|publisher|zipper|zipper-worker|daak ...] [--db <rds name|host[:port]>] [--migrate]`
  - postgres + redis always run (unless `--db`). Choosing `zipper` adds `zipper-worker`.
  - First run builds images (~10 min) and seeds the demo account; later runs take seconds and keep the DB.
  - Seeding happens only when v2 is in the set, the DB is local, and the permission tree is empty.
- `tz local down [--reset]`: stop; `--reset` also deletes the `tz-local_pgdata` volume (next `up` re-seeds). Confirm first.
- `tz local logs [-s ...] [--since 30m] [--follow/--no-follow]`: use `--no-follow` from an agent.
- `tz local restart [-s ...]` / `tz local ps`.

## Ports
v2 8000, reporting 8001, subhub 8003, zipper 8005, Postgres 5432 (`scar3crow` / `apgh2bpb`, db `tranzact`),
Redis 6379. Frontend dev servers point at `http://localhost:8000` as usual.

## Which code runs
- If `~/.tz/config [main]` has the repo's path (`TRANZACT_V2_DIRECTORY`, `TZ_REPORTING_DIRECTORY`, `SUBHUB_DIRECTORY`,
  `ZIPPER_DIRECTORY`, `DAAK_DIRECTORY`, `TZ_COMMS_PUBLISHER_DIRECTORY`), that checkout is **bind-mounted at `/app`** on
  whatever branch it has checked out, uncommitted changes included. Switching the branch in the checkout changes what
  the container serves.
- v2, reporting (runserver), subhub (uvicorn --reload) and the zipper API reload on save. zipper-worker, daak and
  publisher are restarted by a file watcher (`~/.tz/local/watch.pid`, log `watch.log`); `tz local restart -s <svc>` is the fallback.
- No checkout configured → runs from the develop image.
- The image (virtualenv) behind a checkout is rebuilt automatically only when `pyproject.toml`, `uv.lock`,
  `requirements.txt`, `qa/requirements.txt`, `uvscript.py`, the Dockerfile or the CLI docker files change.

## Config
Staging `.env` from Secrets Manager → your checkout's `.env` merged on top (your keys win) → DB/Redis/queues/in-stack
URLs wired to local containers (wins over both). Your `.env` is never written. S3, SES, tz-print are shared staging.
daak uses two SQS queues created per user: `local-<user>-daak-*`.

## `--db` (shared RDS)
Points every service at an RDS instance (`mstag-dmz`, or `host:port`) with `[auth]` creds. No local Postgres, no seed,
**no migrations unless `--migrate`** - the DB is shared with other people, so don't pass `--migrate` casually.
The RDS security group must allow your IP.

## Gotchas
- Container names follow Compose: `tz-local-v2-1`, `tz-local-subhub-1`, etc.
- The container venv is a named volume and does **not** follow a tz-core pin change on branch switch. Fix:
  `docker exec tz-local-v2-1 uv pip install "tz-core==X" --index-url https://<PYPI_USERNAME>:<PYPI_PASSWORD>@pypi.letstranzact.com --no-cache-dir`
  (creds from `~/.tz/config [auth]`, not the container's DB_USER), then `docker restart tz-local-v2-1`.
- Run backend ORM/QA scripts **inside** the container:
  `docker exec -w /app tz-local-v2-1 /app/.venv/bin/python qa/tools/...`. On the host, v2's `app/settings.py`
  loads `.env` with `override=True`, clobbering DB env overrides, so you would write to staging RDS instead.
- `seed.sh` writes `QA_EMAIL='…'` with quotes and `activate_features.owner_email()` doesn't strip them; standalone
  seed-tool runs need `-e QA_EMAIL_OVERRIDE=<email>`.
- Needs ~6 GB of Docker memory for all nine containers; run only the services you need.
